Operating guide

Greenfield development · Brownfield adoption · Verification · Review · Evidence

Documentation baseline: public revision 91c6790. Guide edition: 1.1, 24 September 2026.

This guide explains how to operate FormalSpecGen, choose an appropriate workflow, interpret its results, and retain the evidence needed to review a change. It covers all 38 commands registered by the default CLI, the interactive shell, and the two tools in the default strict MCP catalogue. It is a versioned operating manual, not a claim that every supported command proves an entire application correct.

Edition 1.1 updates the earlier complete guide through the two direct admission-policy commits. The CLI parser is unchanged; admission, evidence fields, profile restrictions, templates, and helper checks were reviewed against 91c6790. The included Java teaching fixtures were syntax-compiled; the formal backends and the complete example workflows were not executed during preparation. Expected outcomes in examples are acceptance targets, not pre-generated proof results. Do not substitute this guide for a new validation run in your environment. S01 S02 S03 S04 S60 S61

New in edition 1.1: invocation-specific permission profiles; requested versus granted effects; policy-bound evidence; per-command strict-MCP availability; and a pinned-policy receipt check. See the admission field guide and edition changelog.

1. Choose your workflow

What the tool does

FormalSpecGen coordinates specification drafting, deterministic transformations, implementation generation, native verification, bounded model checking, and evidence collection. Some operations propose artifacts; some inspect them; some invoke formal tools. Human review decides what the intended contract and assumptions should be. A successful model response is never itself a verification result. S05 S06 S07 S08

Start from the object you actually have, not the strongest-sounding command name.

Starting point Recommended path Review checkpoint
A new feature described in prose draft → review contract → implement → verify Confirm preconditions, outcomes, frames, and assumptions before generating bodies.
A finite stateful component to reuse across languages domain --schema-version 2 → validate-domain → review → promote-domain → canonical draft → implement Accept an exact candidate hash, then retain matching evidence.
An existing repository with little formal documentation analyze-codebase → document-code → review extracted candidates → validate selected models Extraction is incomplete discovery, not approval or proof of the source.
An existing source file with reviewed contracts verify → inspect → approved edit → verify-refactor Keep an immutable baseline and inspect the full semantic diff.
A slow verified algorithm optimize-algorithm or discover-algorithms → preservation/proof gates → separate benchmarks Verification does not establish a performance improvement.
A suspected vulnerability security-inspect / assess-security → review → remediate or correct-behavior Decide whether behavior must remain unchanged or intentionally change.
Several reviewed components compose, then reverify; use system for component workflows Review dependency contracts, bindings, and composition assumptions.
Agent-assisted editing Strict MCP inspect_code and Java verify_code Approve edits; keep the verifier installation and evidence outside agent control.

For a first adoption, choose a small sequential component with explicit boundaries. Do not begin by treating a whole distributed application as one proof obligation. The specialist workflows in chapter 11 have deliberately limited input profiles. S01 S08 S09 S10

2. Understand contracts, claims, and review

The main artifacts

A contract describes allowed inputs, promised results, exceptional behavior, and permitted state changes. A frame condition identifies the state a method may modify. A domain model describes state variables and transitions. An implementation supplies executable bodies. Evidence records what a tool checked, with which inputs, assumptions, configuration, and result.

Preservation checks compare the supported semantic surface rather than treating unchanged method names as sufficient. In the pinned Java and native front ends, unsupported or incompletely represented syntax can be rejected. That is a supported boundary, not an instruction to strip annotations or weaken the contract. S12

Read claims in context

Result category What it can establish What it does not establish by itself
Inspection, extraction, documentation, or transformation A report or artifact was produced under a defined procedure Correctness of the application
Parsing or static checking Accepted syntax/types for the requested checker A postcondition proof
RUNTIME_SAMPLE The recorded tests ran with their observed outcome All possible inputs or executions
BOUNDED_ARCHITECTURE_EVIDENCE Properties of the recorded model within its checked bounds Unbounded behavior or source/model correspondence
DEDUCTIVE_PROOF The supported obligations were discharged under the tool's assumptions That the specification captures every intended requirement
Source/model refinement evidence A supported relation between the checked source and model Unmodeled I/O, arbitrary language features, or external service behavior
NO_PROOF The requested proof is not established by this result Necessarily that the program is incorrect

Result labels differ between workflows. Read status or final_status, claim or claims, request_satisfied where supplied, and the stage evidence. Do not write an integration that searches a log for the word “VERIFIED.” The centralized verification policy distinguishes successful process execution from satisfaction of the requested assurance. S04 S05 S06 S07 S08

Human review is a separate gate

Before accepting a contract or model, check that it admits the intended inputs, describes failure behavior, preserves the required class invariants, and does not hide contradictions or unreviewed assumptions. Review nullness, arithmetic bounds, literal values, imported constants, trusted declarations, and verification-suppression controls where relevant.

For a counter bounded by five, “increment requires value < 5” means callers must establish that condition. It does not mean increment has been specified to throw an exception or return false at five. The example requirements explicitly choose the former semantics. A different product requirement needs a different reviewed contract.

Keep these decisions distinct: approve intended semantics; prove a candidate against them; verify preservation when comparing revisions. verify_code through MCP performs the middle task, not all three. S03 S12 S13

3. Install and configure the tool

3.1 Create a pinned installation

The package requires Python 3.10 or later. The following shell example uses a separate installation directory; do not run it inside an existing checkout with uncommitted changes. S02

# Shell setup, not FormalSpecGen subcommands.
git clone https://github.com/sheelmorjaria/formalspecgen.git formalspecgen-tool
cd formalspecgen-tool
git checkout --detach 91c6790
python3 -m venv .venv
. .venv/bin/activate
python -m pip install -e '.[mcp]'
formalspecgen --version
formalspecgen --help

Omit [mcp] for a CLI-only installation. Installing the Python package does not install OpenJML, TLC, Frama-C, Prusti, or every other judge. Install only the backends required for your intended workflows, then verify their readiness. Use the source-controlled CI workflow as the pinned acceptance-environment reference, not as a universal workstation-provisioning script. S02 S04 S14

The examples use a POSIX shell. Strict execution needs Linux facilities. A Windows or macOS desktop therefore needs a suitable Linux execution host or environment for these strict paths; a Python virtual environment alone is insufficient. Do not silently replace strict execution with unrestricted local commands. S15

3.2 Check readiness

formalspecgen doctor
formalspecgen doctor --judges
formalspecgen doctor --json
formalspecgen doctor --require OpenJML --require TLC --json evidence/doctor.json

Create the output directory first and use the judge names reported by your installed version. doctor --json without a value prints JSON; most other commands require a filename after --json. --require is repeatable. --strict fails when the aggregate report is not ready, which can be too broad for a deliberately minimal installation. A successful readiness report remains environmental metadata, not an application proof. S01 S16

Set configuration in the environment inherited by the CLI or MCP process. The built-in .env reader uses the configured tool home and simple KEY=VALUE lines; it is not a general shell interpreter. Existing environment variables take precedence. Restart a long-running MCP server after changing its configuration. S14

3.4 Provision the strict Linux execution boundary

The strict executor needs Bubblewrap (bwrap), prlimit, usable Linux namespaces, and a cgroup v2 hierarchy with delegated memory/process controls. The administrator must arrange the parent/child cgroup membership correctly; setting a path in an environment variable does not create delegation. Writable /work and /tmp are separately bounded tmpfs mounts. Source inputs and the selected tool resources are read-only. S15

The executor's default policy object uses a 60-second wall limit, 512 MiB memory, 32 processes, 1 MiB output, 64 MiB per-file limit, 128 MiB workspace, and 64 MiB temporary storage. Adapters can override these defaults. These are not universal CLI flags and are not promises that every workflow uses the same values. S15

Provision this on a dedicated runner or service account. Keep the authoritative evidence location outside the sandbox's writable mounts. Do not disable host security policy globally as a routine installation step; resolve namespace and delegation requirements with the administrator. A missing sandbox, inaccessible cgroup, resource failure, or failed cleanup is an execution failure, not a request to retry without isolation.

Scope: the strict Java and generated native runtime paths are not a guarantee that every full CLI workflow and native formal backend has the same boundary. Default MCP deliberately limits execution to isolated Java verification. S03 S15

3.5 Configure generation separately from verification

Pure verification and deterministic inspection do not require an LLM endpoint. Generation, narrative, repair, and some invariant-proposal workflows do. Most generation commands accept --provider and --model; consult the reference because these are not global options. S01 S17

# Example for an already working local Ollama endpoint.
export OLLAMA_BASE_URL=http://127.0.0.1:11434/v1
export OLLAMA_MODEL=YOUR_EXACT_SERVED_MODEL_ID

# Alternative: use --provider openai with a local compatible endpoint.
export OPENAI_BASE_URL=http://127.0.0.1:8000/v1
export OPENAI_MODEL=YOUR_EXACT_SERVED_MODEL_ID
export OPENAI_API_KEY=YOUR_ENDPOINT_AUTH_VALUE

Use a harmless placeholder only when the local endpoint genuinely needs no authentication. Never paste production secrets into project documentation. Supported provider names are glm, openai, and ollama; unknown names fail rather than selecting an unrelated provider. Relevant limits include LLM_TIMEOUT, LLM_MAX_TOKENS, and the Ollama context/prediction settings. S14 S17

Selecting Qwen in AiderDesk configures the outer agent. It does not configure FormalSpecGen's own generation provider. The default strict MCP tools do not run those generation loops, so the first pilot needs only AiderDesk's existing tool-capable endpoint. S03 S17

4. First run: inspect, prove, and reject a bad candidate

Use the bundled project at examples/guide_demo/. Activate the pinned tool environment, then change to that directory. All paths below are relative to it.

mkdir -p evidence
formalspecgen inspect src/BoundedCounter.java --json evidence/inspection.json
formalspecgen verify src/BoundedCounter.java --mode esc --json evidence/valid.json

The first command performs deterministic Java inspection. The second requests deductive checking of the submitted Java contract and implementation. With a correctly provisioned backend, the intended-correct fixture should satisfy the request. Read the actual verdict rather than assuming success from this document. S01 S18

Now exercise the negative path:

formalspecgen verify negative/BoundedCounter.java --mode esc --json evidence/invalid.json

The negative fixture adds two instead of one. It is expected to fail the postcondition check, potentially also the invariant at the upper boundary. A nonzero exit is the desired result for this negative test. Do not weaken the specification to make the test pass.

Finally check a body-only revision:

formalspecgen verify-refactor baseline/BoundedCounter.java refactored/BoundedCounter.java --json evidence/refactor.json

The candidate changes only assignment syntax. The expected result is a preserved supported contract plus successful backend checks. Both revisions keep the public class name and filename BoundedCounter.java; compile or verify them as separate revisions, not simultaneously in one class output directory. S12 S19

Completion check: you have a genuine successful verification, a genuine failed verification, and a separately checked preservation result. You have not yet demonstrated architecture refinement, thread safety, performance, or an MCP transport round trip.

5. Greenfield: requirements to implementation

Interface: operator-facing CLI workflow. The complete workflow is not admitted to default strict MCP. Java inspection or verification can be used separately under their own profiles; that does not authorize the surrounding steps. S48 S56

This route suits a new component whose method contracts are the immediate goal.

Step 1 — Write requirements and clarify behavior

State valid inputs, initial state, failure outcomes, state changes, arithmetic bounds, external dependencies, and concurrency assumptions. Assign identifiers such as REQ-001 for later traceability. Avoid requirements that say only “safe,” “correct,” or “secure” without defining observable behavior.

formalspecgen draft "A sequential counter starts at zero, stays between zero and five, increments only below five, and decrements only above zero." --provider ollama --lang java --out runs/counter-draft-001

draft takes the requirement text, not a path to a requirements file. Answer its clarification questions and inspect the generated file location in the result. For Java generative drafting, use the reported run output; --out-file is primarily for native/canonical paths. Use a fresh run root for each evidence-bearing attempt. S01 S05

Step 2 — Review and freeze the contract

Read every precondition, postcondition, invariant, frame, assumption, and semantic annotation. A draft accepted by OpenJML's checking stage is not an implementation proof. Preserve the reviewed file as the trusted input. Use --no-clarify only when clarification has already happened; it does not approve missing semantics.

Step 3 — Generate an implementation at an explicit scope

For a method-contract-only starting point:

formalspecgen implement reviewed/Counter.java --provider ollama --method-proof-only --max-attempts 5 --out runs/counter-implementation-001 --json evidence/implementation.json

reviewed/Counter.java is the contract file you actually approved, not a bundled filename. This explicit mode skips architecture/TLC and source-refinement claims. It is often preferable to requesting critical architecture assurance for an unsupported domain and then weakening gates when it fails. S06

For a supported architecture and reviewed V2 binding, use the stronger route in chapter 6 instead. The general profile behavior is:

Profile / mode Java route Native route
lightweight Specification lint and compilation-oriented implementation path Static checking without the standard runtime sample
standard Static contract checking plus required RAC/JUnit sample Static checking plus required instrumented runtime sample
critical ESC, required bounded architecture evidence, and supported refinement gates Native formal checking, with refinement only where supported and evidenced
--method-proof-only Explicit ESC against method contracts without architecture/refinement Narrows the stated scope; it does not add missing backend capabilities

The returned stage evidence is authoritative. Profile names do not make evidence interchangeable across languages. Java standard assurance is not Java critical assurance; a passing runtime sample is not deductive proof. S06 S07 S08

Step 4 — Review, verify, and integrate

Inspect the complete candidate diff, not just the method body visible in a chat message. Verify the exact file you intend to merge. Retain the approved contract, output source hash, final verdict, actual execution observations when supplied, and any published receipt. Run your ordinary application tests as a separate check of integration requirements.

Do not automatically approve --accept-pass entries. Postprocessing can alter proof-relevant semantics; accepted transformations need explicit review, and the final artifact is checked against the supported trusted surface. S07 S12

6. Greenfield: reviewed V2 domain to source

Interface: operator-facing CLI workflow. The complete workflow is not admitted to default strict MCP. Java inspection or verification can be used separately under their own profiles; that does not authorize the surrounding steps. S48 S56

This route is for a bounded state machine whose semantics should drive multiple deterministic outputs. V2 uses typed integer/boolean state, guards, effects, frames, and invariants. The supported scope is smaller than an arbitrary programming language and rejects malformed or unsupported models. S13

Step 1 — Create a candidate

Interactive generation:

formalspecgen domain "A sequential bounded counter from zero through five" --schema-version 2 --provider ollama --project-root .

The default domain schema is 1, so explicitly choose 2 for this workflow. V1 is the older plugin/scaffold path; do not confuse its scaffold with a reviewed V2 artifact. The V2 workflow may already emit validation evidence. Revalidate after every candidate edit. S01 S20

The bundled alternative is domains/candidates/bounded_counter.v2.yaml. It is explicitly unreviewed and includes no fabricated promotion digest or signature. Its operations use void / unavailable: an operation is enabled only when its guard holds.

Step 2 — Validate by module name

formalspecgen validate-domain bounded_counter --project-root . --emit-tla evidence/BoundedCounter.tla

Pass the module name, not an arbitrary YAML path. This command has no --json option. Inspect the reported validation file, emitted model, reachable-state/bounds information, and counterexample or failure details. Validation checks the candidate; it does not supply human approval or prove correspondence to separately written source. S20 S21

Step 3 — Review the model and exact candidate identity

For the example, confirm the range [0, 5], initial value 0, one actor, increment/decrement guards, one-state-variable frame, and the absence of an implied “return false” or exception at the boundary. Review all changed bytes after the last validation. Read candidate_sha256 from that validation and verify it identifies the candidate you actually reviewed.

Promotion is deliberately a human checkpoint:

formalspecgen promote-domain bounded_counter --project-root . --schema-version 2 --accept-candidate-sha256 REVIEWED_64_HEX_DIGEST

Replace the placeholder manually with the reviewed digest. Do not automate “read latest hash and approve it” in an agent workflow. Use --replace-reviewed-domain only for an intentional reviewed replacement. --force during candidate work is not the same as authorization to replace a reviewed domain. S22

The promoted JSON is written under domains/v2/. Keep the candidate, its validation evidence, and promotion provenance together. An edit after validation invalidates the old evidence; an edit after promotion requires a new reviewed revision.

Step 4 — Deterministically render a reviewed domain

Run from the project containing domains/v2/:

formalspecgen draft "Render the reviewed bounded counter" --canonical-domain bounded_counter --lang java --out-file generated/BoundedCounter.java --no-clarify

The canonical route consumes the reviewed domain rather than asking an LLM to reinterpret it. The prose is still a required positional argument. Java, Rust, C, and C++ are selectable on this route; C++ drafting requires a canonical domain at this revision. S01 S23

Step 5 — Check implementation and source/model linkage

formalspecgen implement generated/BoundedCounter.java --provider ollama --assurance-level critical --v2-reviewed-domain domains/v2/bounded_counter.json --v2-validation-evidence domains/candidates/bounded_counter.v2.validation.json --out runs/counter-v2-001 --json evidence/counter-v2.json

Use the actual validation path reported locally. The two V2 arguments form a pair. They are not interchangeable with a generic architecture report. Native deterministic V2 outputs take a different verification path from free-form native synthesis; read the actual claim and unsupported-boundary reports. S06 S07 S08

Step 6 — Add traceability

formalspecgen generate-traceability-matrix domains/candidates/bounded_counter.v2.yaml src --reqs requirements.txt --out evidence/traceability.md --json evidence/traceability.json

Review unmatched or ambiguous rows. A matrix connecting REQ-### identifiers, invariants, and source locations is a review artifact, not a certificate that every requirement was implemented. S24

7. Brownfield: understand and specify an existing project

Interface: operator-facing CLI workflow. The complete workflow is not admitted to default strict MCP. Java inspection or verification can be used separately under their own profiles; that does not authorize the surrounding steps. S48 S56

The starting point is executable code and existing behavior, not a clean specification. Preserve the repository baseline and its tests before extracting or editing contracts.

Step 1 — Record the baseline and select a component

Use a branch or worktree and keep the original source revision. Identify externally visible behavior, error handling, persistent state, dependencies, and concurrency. Start with a component small enough to review rather than treating extraction output as a complete architecture.

Step 2 — Extract an inventory and candidate models

formalspecgen analyze-codebase src --out-dir extracted --project-root . --json evidence/extraction.json

This command can create unreviewed domain candidates and architecture/extraction reports. “EXTRACTED” is not “VERIFIED.” Read its limitations, skipped constructs, and source associations. Bounds, initial values, reset transitions, omitted calls, and approximated operations are review obligations. Do not overwrite your understanding of the production system with whatever subset the extractor recognizes. S25

Step 3 — Produce deterministic documentation first

formalspecgen document-code src/BoundedCounter.java --no-llm --out evidence/counter-documentation.md --project-root . --json evidence/documentation.json

This documents the application's extracted model. It does not generate this tool manual, establish extraction completeness, or prove the original source. Remove --no-llm and select a provider only when you also want an explanatory narrative; that narrative adds no formal evidence. S26

Step 4 — Reconcile the extracted model with reality

For each chosen candidate, review what is represented and what is not. Reconcile existing tests and requirements with the extracted guards/effects. Add or revise contracts deliberately, retaining a record of whether you are documenting established behavior or changing it.

Validate the candidate by its generated module name. Promotion can follow chapter 6 after review. Separately verify the original source against its reviewed contracts. A checked model and a checked source do not establish correspondence unless the supported refinement path also runs successfully. S20 S21 S22 S25

Step 5 — Decide between preservation and correction

Choose a preserving refactor when callers must retain the same contract. Choose a behavior-correction workflow when you intentionally change accepted inputs, limits, error handling, or side effects. Record the distinction before generating patches. Do not call stronger preconditions a harmless optimization: they can exclude calls that were previously allowed.

Adoption completion check: the component has a reviewed baseline, documented assumptions, a known supported proof scope, negative tests, a verification result for the source, and a separate record for any model validation/refinement. Proceed component by component. S12 S19 S27

8. Brownfield: refactor and optimize without changing the contract

Interface: operator-facing CLI workflow. The complete workflow is not admitted to default strict MCP. Java inspection or verification can be used separately under their own profiles; that does not authorize the surrounding steps. S48 S56

Inspection and targeted transformation

formalspecgen inspect src/Service.java --json evidence/service-inspection.json
formalspecgen apply-refactor src/Service.java --inspection evidence/service-inspection.json --pattern extract-method --method process --out refactored/Service.java --json evidence/refactor-action.json
formalspecgen verify-refactor baseline/Service.java refactored/Service.java --json evidence/preservation.json

These are application-specific templates: the bundled counter is intentionally too small to demonstrate a long-method extraction. Use a method the inspection actually identifies. The Java transformation consumes a source-hash-bound inspection; rerun inspection when the source changes. Candidate generation is not the preservation verdict. S18 S19 S28

The parser lists extract-method, factory-method, state, decorator, facade, null-object, and strategy. Their availability depends on the recognized source shape and language. Native transformation support is narrower: extract-method and a supported Rust strategy path. Do not assume every inspection finding has an automatic transformation.

For supported Java helper extraction, the candidate may be a directory of collaborating .java files. Keep the baseline's primary class filename and include the exact files to be checked. Private helpers are allowed within the supported boundary; new assumptions, skipped verification, or changed public contracts are not ordinary helper extraction. S12 S19

Optimization and multi-strategy discovery

formalspecgen optimize-algorithm baseline/TwoSum.java --strategy hashmap --out optimized/TwoSum.java --provider ollama --json evidence/optimization.json
formalspecgen discover-algorithms baseline/TwoSum.java --strategies hashmap,two_pointer --max-workers 1 --provider ollama --out-dir discovered --json evidence/discovery.json

Use a reviewed Java algorithm matching the lane's supported shape. The optimizer accepts nested_loop in its argument choices but rejects it as a potential regression; it is not a usable optimization recommendation. Discovery supports its own wider strategy registry, listed in the command reference. A verified candidate still needs separate performance measurements and integration testing. S29 S30

Two different meanings of “equivalence”

verify-bisimulation is only an input and public-surface preflight. Its mapping connects state labels to source class names. Its successful result remains NO_PROOF and explicitly reports that behavior/heap equivalence was not proved. The bundled mappings/preflight.json demonstrates that schema. S31

formalspecgen verify-bisimulation baseline/BoundedCounter.java refactored/BoundedCounter.java mappings/preflight.json --json evidence/preflight.json

prove-equivalence checks finite V2 transition systems against an explicit relation. Its mapping schema is different: an object with a states list of baseline_state / refactored_state pairs. S32

formalspecgen prove-equivalence domains/candidates/bounded_counter.v2.yaml models/equivalent_counter.v2.yaml --mapping mappings/states.json --json evidence/model-equivalence.json

The bundled example uses the identity relation on values zero through five. A successful bounded-model result does not prove Java heap equivalence, timing, external I/O behavior, or arbitrary program equivalence.

9.3 Compose reviewed domains

After the example domain has been validated, reviewed, and promoted:

A composition plan has system_name, architecture, bindings, and use_cases. Each binding connects a declared component ID to a promoted module. Each use case names ordered steps. The bundled plan uses one reviewed counter component with separate increment and decrement use cases. It is not a pre-proved composition. S09

10. Security assessment, remediation, and intentional correction

Interface: operator-facing CLI workflow. The complete workflow is not admitted to default strict MCP. Java inspection or verification can be used separately under their own profiles; that does not authorize the surrounding steps. S48 S56

Use these workflows only for code you own or are authorized to assess. Keep assessment reports, proposed patches, and any test templates tied to the exact target revision.

Assess and triage

formalspecgen security-inspect src/Service.java --json evidence/vulnerabilities.json
formalspecgen assess-security src/Service.java --json evidence/security-assessment.json

security-inspect differs from the deterministic inspect: it can invoke formal/security tools and prepares a vulnerability report. Its zero exit means the report was produced, not that there are no findings. assess-security --no-sast explicitly reduces scope. Even a scoped VERIFIED_SECURE result is not immunity from every weakness. S01 S37

Generate review-only tests for findings

formalspecgen security-exploit evidence/vulnerabilities.json src/Service.java --out-dir security-pocs --json evidence/poc-generation.json

This generates supported local proof-of-concept source templates. The status can be POCS_GENERATED while the claim is POC_GENERATED_NOT_EXECUTED. The command does not compile, run, or transmit those templates. A generated test is not a demonstrated exploit. Review and authorize any subsequent execution separately. S38

Patch while reviewing the original contract

formalspecgen remediate src/Service.java evidence/vulnerabilities.json --provider ollama --out-dir remediated --json evidence/remediation.json

The workflow writes a separate candidate. Review the diff, the report's provenance, and the native verdict. A successful patch verification does not automatically establish preservation of all original behavior or prove that every reported issue was addressed. Use the preservation workflow separately when that is required. S39

Deliberately change behavior

formalspecgen correct-behavior src/BatchRunner.java --cwe CWE-400 --strategy bound-loop --provider ollama --out-dir corrections --json evidence/correction.json

This is not a preserving refactor. It can strengthen contracts or introduce bounded/error behavior. The explicit strategy choices are:

Strategy Review focus
bound-loop, bounded-cache, bounded-pool Chosen limits and what happens at capacity
static-pool Hardware profile, element size, derived capacity, and allocation behavior
checked-math Overflow/error semantics

12.5 Understand permission attenuation

A matching profile defines the maximum permissions available, not an automatic grant of them all:

Granted effects = Explicitly requested effects ∩ Profile effects
Boundary allowed = Required effect is in granted effects

For example, an internally admitted request that asks only for workspace_read cannot execute a verifier or publish evidence, even if its matching profile supports those effects. Unknown effects, wrong modes/backends, or disallowed providers do not become partial approvals. The current verify_code handler requests all three verification effects; inspect_code requests reading alone. S03 S55 S58

There is no --effects CLI flag or MCP effects argument in this baseline. Narrower requests are an internal integration mechanism; the eight effect-subset tests check that omitted permissions cannot reappear later. See the admission field guide for definitions, failure handling, and the requirements for admitting future workflows. S58

13. Publish, validate, and review evidence

Distinguish the output kinds

An ordinary --json output is a verdict file. A ledger-backed run contains an evidence/ directory, run identity artifact, transition artifacts with a hash chain, and a terminal manifest. The strict Java MCP response additionally returns an evidence receipt identifying the manifest. Not every CLI command publishes that same receipt. S03 S11

A typical strict MCP layout is:

.formalspecgen/mcp-evidence/<run-directory>/
└── evidence/
    ├── run.json
    ├── 001-....json
    ├── ...
    └── manifest.json

The terminal manifest is published last. An incomplete run is not a successful evidence-bearing result. Publication failure downgrades the strict MCP outcome rather than silently returning a proof without its required receipt. The receipt is the MCP response’s evidence object and contains run_id, manifest_path, manifest_sha256, and publication_status. S03 S11

Validate a receipt with trusted tooling

There is no built-in formalspecgen validate-evidence command at this revision. The package supplied with this guide includes an auxiliary tools/validate_receipt.py wrapper around the actual RunLedger.validate API. Run it from a trusted tool environment, not as arbitrary code supplied by the candidate.

python /path/to/guide/tools/validate_receipt.py evidence/mcp-response.json --evidence-root .formalspecgen/mcp-evidence --require-admission

The input can be the saved structured MCP response or its receipt object, not a chat transcript or the outer JSON-RPC envelope. The script checks that the manifest is inside the specified evidence root, matches the received digest, and agrees on run identity, then calls the ledger validator. With --require-admission, it also checks the manifest's admission summary against the two-profile snapshot bundled for 91c6790, recomputes the profile digest, verifies requested/granted-effect consistency, and compares response metadata when present. For an independently retained manifest digest, add --expected-manifest-sha256 DIGEST.

A successful ledger validation establishes internal consistency with the selected receipt, not authenticity against a privileged attacker who can replace both the ledger and the receipt. Retain a trusted copy of the receipt/digest, or use your signing and storage policy. The publication guarantee is application-level write-once/no-replace, not a claim that a host administrator cannot alter the filesystem. S11

Read the admission fields in evidence

The response's mcp_admission object is also stored at terminal.mcp_admission in the manifest and details.mcp_admission in the proof-stage artifact. The receipt itself remains the small evidence object; policy metadata is not a replacement receipt. S03

Field inside mcp_admission Review meaning
profile Named invocation profile, not a whole-command safety label
mode, language, backend, provider Selected invocation; current admitted provider is JSON null
requested_effects Effects explicitly requested by the handler
granted_effects The request/profile intersection; never infer missing permissions
profile_definition Canonical ceiling: name, modes, languages, backends, effects, providers, output scope, evidence requirement
profile_sha256 SHA-256 of the canonical definition's compact, sorted-key UTF-8 JSON
admission_policy_version mcp-admission-v2 for this baseline; distinct from package and guide versions

Array-valued fields in the canonical definition are sorted and deduplicated. The digest uses ensure_ascii=False and separators (',', ':'). A policy name may remain constant while its contents change, so retain the definition and digest together. S55

The helper's success means receipt/ledger integrity and, when requested, agreement with this edition's approved policy snapshot. It does not rerun the proof, authenticate an attacker-replaceable receipt, approve the specification, or compare the source with your independent baseline. Legacy evidence without admission metadata may still be checked in integrity-only mode, but it must not be described as satisfying the new policy check. An upgrade to profiles or policy version requires an explicit review and a matching guide/helper update.

Review the result and the execution separately

Before accepting a verification result, establish that the requested mode and proof scope succeeded, that required execution policy was enforced, that the receipt validates, and that the recorded source snapshot is the revision being reviewed. Resource failures, instrumentation-startup failures, missing tools, unsupported syntax, and publication failures remain NO_PROOF rather than candidate counterexamples. S03 S15 S50

Use unique run/output roots. Do not delete an earlier manifest merely to make a rerun succeed in the same directory. Mutable reports and “latest” convenience paths are not authoritative evidence identities.

Reviewer keys and signed artifacts

formalspecgen manage-trust --add-key reviewer-public.asc
formalspecgen manage-trust --list
formalspecgen sign-artifact domains/v2/bounded_counter.json --key REVIEWER_KEY_ID

These are human-operated actions. GPG must be installed and the signing key must be available through your approved key-management process. Promotion can sign with --signing-key; verify-refactor --signing-key requires a JSON destination. S22 S51

The default registry is trusted_keys.json; AUTHORIZED_REVIEWER_KEYS contributes to the authorized set. A custom manage-trust --registry file is not automatically selected by every downstream caller. Configure the registry at the location actually consumed by your verification path. With no authorized-key policy, signature verification can accept any verifying key; signature validity alone is not an approved-reviewer policy. 14. Automate safely in development and CI

Use command outcomes, not generic success assumptions

For direct verify, the exit status reflects whether the requested semantic decision is satisfied. Other commands have different contracts: documentation/extraction can succeed without proof; security-inspect can succeed while reporting findings; verify-bisimulation can succeed at preflight only; and a correction can successfully generate an unproved capacity candidate. S01 S04 S31

For every automated job, define the expected workflow result before running it. Parse the relevant structured fields. Fail on absent, unknown, or weaker claims rather than treating them as compatible. Save stderr, the exact invocation, tool versions, source revision, and evidence references. Run negative tests as well as positive tests.

A small application-level gate

set -eu
mkdir -p evidence
formalspecgen verify src/BoundedCounter.java --mode esc --json evidence/verification.json
formalspecgen verify-refactor baseline/BoundedCounter.java refactored/BoundedCounter.java --json evidence/preservation.json

This is a shell fragment for the bundled demo on a provisioned runner. It is not a declaration that ordinary CLI JSON has an MCP receipt. Do not add || true to these release gates; handle deliberate negative tests in separate jobs or explicit expected-failure assertions.

Keep real acceptance tests mandatory on the provisioned runner

The pinned repository separates the Python matrix, strict-offline Rust checking, and real Linux sandbox/OpenJML acceptance. The strict-offline stage prefetches locked Cargo dependencies first, then enforces offline checking. MCP admission & permissions

User-guide edition 1.1 · FormalSpecGen revision 91c6790 · Admission policy mcp-admission-v2

This field guide accompanies the operating guide and complete CLI reference. It explains the current user-facing boundary and how to review the policy metadata returned by a tool. It is not a mechanism for installing or granting new server permissions.

A1. Choose the interface before the workflow

The full CLI remains available to an operator. Strict MCP is a smaller interface: it admits particular combinations of command, mode, language, backend, provider policy, and effects. Installing a judge, enabling a tool in a client, or finding a Python handler does not create an admitted combination. S01 S48

Task Strict MCP at this revision Other supported route
Inspect Java inspect_code CLI inspect
Parse, check, or prove submitted Java/JML verify_code; parse, check, esc respectively CLI verify
Diagnose tools Not admitted: doctor_environment launches probes Operator CLI doctor
Create contracts or implementations Not admitted Greenfield CLI recipes in chapters 5–6
Extract, document, refactor, or optimize a repository Not admitted Brownfield CLI recipes in chapters 7–8
Check native or composed systems Not admitted Scoped CLI workflows in chapters 9–11
Promote, sign, or change reviewer trust Human-only; cannot acquire an MCP profile Reviewer-operated CLI

The current profiles do not call a FormalSpecGen LLM provider. Qwen's access through AiderDesk is a separate client-side configuration and data-flow decision. No provider setting in the shell changes these profiles into generation workflows. S03 S17 S48

A2. Permissions are independent

Effect name What it authorizes Current profile use
workspace_read Read an approved input inside the workspace boundary Both tools
external_execution Reach the admitted compiler/verifier execution path Java/JML verification only
evidence_publication Publish a new immutable verification ledger and receipt Java/JML verification only
workspace_write_new Produce ordinary new artifacts in a designated output scope Not granted by current profiles
provider_access Contact an explicitly allowed provider Not granted by current profiles

Publishing verification evidence is not permission to edit source files. Read-only inspection is not permission to invoke version probes. A future deterministic generator would still need write authorization; a future LLM-assisted generator would additionally need provider authorization. Those are future admission decisions, not enabled modes in this release. S16 S48 S56

The loader rejects profiles with unknown effect names or output scopes, providers without the corresponding permission, provider access without an allowlist, writes without the designated output scope, and external execution in a non-executing classification. Trust actions cannot receive profiles. S48 S57

A3. Understand request-level attenuation

A profile is a ceiling. A successful internal admission receives only the effects explicitly requested within it:

granted_effects = requested_effects ∩ profile.effects

For the verification ceiling, a request containing only workspace_read remains read-only. Execution and publication checks reject it. For a rejected admission, the granted set is empty. The effect-subset tests cover all eight combinations of the three verification effects. S58

The public tools do not accept an effects, backend, provider, or profile argument. The server's verify_code handler requests reading, execution, and evidence publication together. inspect_code requests reading only. Send only the documented tool arguments: S03

{"file_path": "src/BoundedCounter.java", "mode": "esc"}

For inspection, send only file_path. Do not add policy fields copied from returned metadata. Adding an unknown or disallowed effect internally is a rejection, not a request that is quietly trimmed into permission. S55

A4. Interpret admission and evidence together

mcp_admission identifies the selected profile and invocation, the requested and granted effects, the canonical definition, its SHA-256, and the policy version. In a published verification run, the same summary appears in the response, manifest terminal metadata, and proof-stage details. Inspection returns findings and admission metadata, not a verification receipt. S03 S55

Use the metadata as an audit record, not as a capability token to submit with a later call. A profile digest identifies contents; it is not a reviewer signature. A committed receipt identifies publication; it does not establish that the proof succeeded or that you approved the specification.

The example examples/templates/admission-metadata.example.json contains illustrative metadata derived from the pinned profile. It deliberately has no run identifier, proof result, manifest, or receipt.

To check a real saved response from your deployment:

python /path/to/guide/tools/validate_receipt.py \
  /path/to/mcp-response.json \
  --evidence-root /path/to/project/.formalspecgen/mcp-evidence \
  --require-admission

This is a guide-pack helper, not a FormalSpecGen subcommand. It validates receipt/ledger consistency with the trusted installation and checks admission metadata against docs/admission_profiles.json. Retain the guide/helper and any independently trusted manifest digest outside the agent's editing authority. The helper does not rerun a verifier, establish receipt authenticity, or decide whether the submitted contract is the right requirement.

A5. Handle rejections without widening authority

A profile mismatch returns ISOLATION_UNSUPPORTED, NO_PROOF, and an unsatisfied request. A concrete boundary can also reject an omitted effect even after profile matching. An unavailable cgroup, tool failure, or failed publication is a different operational failure; neither permits unrestricted fallback. S03 S55

Keep the failed result and its diagnostics. Correct an accidental mode or path, or ask the operator to repair the host. Do not set strict mode to 0, substitute a legacy route, or ask the agent's shell to perform the same blocked workflow. AiderDesk's shell approvals and the MCP server's permissions are separate controls.

For a brownfield refactor, use the operator CLI preservation workflow and retain its baseline. For greenfield generation, review the proposed contract and provider use outside the strict MCP tools. A successful later verify_code call checks the submitted artifact; it does not retroactively approve the preceding workflow or prove preservation of another contract. S19

A6. Admit future workflows deliberately

For maintainers, each additional profile needs one of two reviewed paths. Executing workflows need the approved execution and publication chain for every reachable stage. Genuinely non-executing workflows need bounded processing and explicit limits on reading, writing, and provider access. A top-level label is insufficient when a child stage can launch a command or export source. S56

Before exposing a profile, document its full invocation tuple, permissible effects, output scope, evidence obligation, and human review step. Test mismatched modes/backends/providers, undeclared writes or execution, indirect dispatch, and failed publication. Keep actual backend acceptance distinct from client-transport testing. A human-only action remains human-only even when it could run inside a sandbox. S57

A7. Upgrade a pilot from the earlier guide

Pin the separate service installation to 91c6790, retain administrator-provisioned sandbox/cgroup configuration, and reload the client connection. Confirm that only two FormalSpecGen tools appear. Run one valid proof, one invalid implementation, and one unsupported native request through the actual client. Save their structured responses; validate the committed verification receipts and admission metadata with the updated helper.

The public CI summary for 91c6790 reports success across five jobs, including real sandbox/OpenJML acceptance. That is upstream evidence about the pinned build, not a record of your local deployment or an AiderDesk/Qwen transport session. S59

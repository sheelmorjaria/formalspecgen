What is available

Admission is not completion. The generated registry tells you which invocation profiles the server will admit. A workflow is complete only when revision-bound CI acceptance demonstrates argument, permission, semantic, and real MCP transport parity.

The live inventory currently maps all 38 CLI commands and 205 argument declarations. The generated baseline reports four CLI commands with at least one admitted profile: inspect, document-code, verify, and unsigned verify-refactor. The refactor command remains incomplete until authenticated signing parity exists.

Use the generated CLI inventory and generated strict capability reference for the exact static catalogue. The repository parity report is the human-readable baseline.

The prior Pages manual is retained as the 91c6790 historical edition. It describes the earlier two-tool Java-only pilot and is not current operational guidance.

Multi-language verification

verify_code accepts source, mode, backend, and optional result_export. The server derives language from the source and admits only declared combinations.

Java / JML

OpenJML parse, check, and ESC. Successful ESC may produce a deductive-proof claim under its recorded assumptions.

Rust

Rust checking plus Prusti or Kani. Kani retains bounded-evidence limits.

C / ACSL

Frama-C ESC through strict execution. Unsupported modes fail explicitly.

C++

ESBMC with recorded bounds. A bounded result is never presented as unbounded proof.

{
  "source": "src/Counter.java",
  "mode": "esc",
  "backend": "openjml",
  "result_export": "verification/counter.json"
}

Exports are new artifacts under the configured MCP output root. Existing destinations are not replaced. Tool startup, sandbox, resource, or publication failures remain NO_PROOF.

Contract-preserving refactoring

verify_refactor compares a reviewed baseline with a candidate file or collaborator directory, preserves contract/proof-trust/semantic-context checks, and verifies both sides using the strict executor. Its evidence bundle binds both snapshots and all actual execution observations.

{
  "baseline": "src/Counter.java",
  "refactored": "candidate/Counter.java",
  "result_export": "refactor/counter.json",
  "signing_intent": false
}

Unsigned Java/JML, Rust, C, and C++ profiles are admitted. Setting signing_intent to true returns APPROVAL_REQUIRED; MCP and the supervisor never receive a signing key. This useful unsigned profile does not make the complete CLI workflow parity claim.

Inspection and documentation

Inspection

{
  "source": "src/Inventory.java",
  "result_export": "inspection/inventory.json"
}

Inspection is an unreviewed analysis result, not proof. Omit result_export for a read-only invocation.

Documentation

Documentation defaults to provider-assisted operation: no_llm=false and provider="ollama". Use no_llm: true when source-derived material must remain provider-free.

{
  "source": "src/Inventory.java",
  "out": "docs/inventory.md",
  "project_root": "inventory-docs",
  "no_llm": true,
  "result_export": "results/inventory.json"
}

Provider, model, and disclosure permissions are independently enforced. Generated documentation remains unreviewed and does not prove the described behavior.

A2A worker coordination

Four MCP-only tools submit, observe, retrieve, and cancel bounded worker tasks: submit_work_item, get_work_item, get_work_artifacts, and cancel_work_item.

A worker result is a proposal. Task completion is not implementation acceptance, formal proof, or permission to merge. Protected paths, child authority attenuation, cancellation intent, terminal-state preservation, and uncertain dispatch remain controller-managed state.

Supervised agent runs

The MCP-only supervisor tools are start_agent_run, get_agent_run, resume_agent_run, and cancel_agent_run. The model proposes typed actions; the trusted gateway authorizes effects and invokes admitted services.

Start with the supervised-engineer profile. The supervisor may inspect, verify, and coordinate within its recorded goal contract, but it cannot change trusted specifications, broaden its permissions, sign artifacts, or merge changes.

Evidence and operational checks

Consumers must separately check the workflow outcome, enforced execution policy, source identity, and publication receipt. A successful model or worker message is not authoritative evidence.

The last reviewed coordination baseline was d9f370b, with public CI run 36211006530. New completion claims must point to their own tested revision and CI artifact; the static Pages build does not create such evidence.
